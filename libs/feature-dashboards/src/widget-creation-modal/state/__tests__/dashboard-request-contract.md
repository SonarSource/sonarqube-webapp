# Dashboard request contract

These snapshots are intentionally fragile. They are a long-running warning when a
valid widget starts fetching different data, changes its filters, adds/removes a
request, or changes request order. Legitimate product changes should update them
after the request differences have been reviewed. Do not loosen the assertions
just to make a refactor pass.

## What runs

`dashboardRequestCases.ts` starts with the real configurator's creation matrix,
applies its metric/slice and platform restrictions, and validates the selected
properties against the current widget schemas. A fixed seed (`0x62634`) chooses
coverage representatives and further samples. Coverage includes every offered
metric and supported scope, all six widget types, history ranges, grouping,
filters, custom pie statuses, trend/breakdown flags and offered top-list limits.

The tests render real widget wrappers and execute real query adapters, queries,
HTTP clients and serialization. Context, feature flags, metric metadata and chart
painting are stubbed; MSW supplies fixed, nonempty response data so dependent
requests, including top-list trend requests, also execute. No history API or
generated SDK functions are mocked.

Every widget starts with a cleared query cache, retries disabled and the clock
fixed at `2026-08-30T12:00:00.000Z`. Both test configurations set UTC. Snapshots keep
the method, path, decoded query pairs and body, preserving request sequence,
duplicates, empty parameters and repeated-value order. Only origin, query-key
ordering and equivalent percent encoding are ignored. Raw URLs remain available
in optional trace files.

Snapshot values are compact JSON strings to keep each widget's contract on one
line. The adjacent case ID identifies its configuration. These tests cover
initial widget fetches, not every interaction: they do not replace drilldown,
retained-client edit, multi-widget cache or response/rendering tests.

## Initial migration audit

The baseline snapshots were generated by running the same new harness on
`77b4bfeae1c4f16745723232badd68b77d10c30f`, immediately before the API migration.
They were then copied unchanged to `578eabcd1b4ca83e903129896ce16a20f3fada85`
and compared without snapshot updates. The complete widget inputs were identical.

| Product                                                   | Widget cases | HTTP requests | Unexpected differences |
| --------------------------------------------------------- | -----------: | ------------: | ---------------------: |
| Cloud: projects and portfolios                            |          406 |           455 |                      0 |
| Server: projects, portfolios and applications, both modes |          956 |         1,908 |                      0 |

All Server requests matched, including order. The only Cloud differences were 24
SCA cases: `entityType=portfolio/project_branch` became the uppercase enum values
declared by the generated contract. Micronaut accepts both casings and binds
them to the same backend enum, so this is a canonicalization change.
Only those 24 snapshot values were amended; the test does **not** normalize SCA
casing or allow arbitrary differences. All request counts and ordering matched.

Repeated baseline and candidate runs produced identical traces within each
revision. Deliberately changing the legacy issue-count API to request a different
entity also caused the snapshot test to fail, confirming that it detects real
outgoing request changes. The reference implementation was restored afterward.

`dashboard-request-baseline.json` records the revisions, seed, harness
hashes, original snapshot hashes, audit totals and amended case IDs. That file
documents the initial migration audit; it is not a requirement to preserve the
initial catalog forever.

## Running and updating

From the repository root:

```sh
node node_modules/.bin/jest -c private/apps/sq-cloud/config/jest/jest.config.js \
  --runInBand --testPathPatterns=dashboard-request-equivalence-test --ci

node node_modules/.bin/jest -c apps/sq-server/jest.config.js --runInBand --ci \
  --runTestsByPath \
  apps/sq-server/src/main/js/apps/projectDashboards/components/__tests__/dashboard-request-equivalence-test.tsx \
  private/libs/sq-server-features/src/feature-dashboards/__tests__/dashboard-request-equivalence-test.tsx
```

Set `DASHBOARD_REQUEST_TRACE` to save complete JSON traces. Cloud writes that
filename directly; Server appends `.server-project.json` and
`.server-portfolio.json`.

When a failure is intentional, inspect the case properties and request changes,
update fixed response fixtures if the new request needs different data, then
replace `--ci` with `--updateSnapshot` for the affected suite. Review the resulting
snapshot diff. A new metric or configurator change can legitimately change the
sample corpus as well as its requests.

For another migration audit, copy the **same** harness files into a checkout of
the reference revision and generate snapshots there first. Compare on the target
revision without updating them. Check that case IDs and complete configurations
match before interpreting request differences. Do not generate the reference
expectations from the implementation being tested.
